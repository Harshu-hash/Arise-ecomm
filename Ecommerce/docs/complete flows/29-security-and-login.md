# Security and Login

## What Is This?

Keeping the platform safe means making sure only the right people can access the right features. This document explains how login works for each role, how the system prevents unauthorized access, and the safety measures built into deliveries and payments.

---

## Who Should Read This?

Anyone setting up or operating the platform who needs to understand how security works.

---

## Login Methods by Role

| Role             | Login method      | Details                        |
| ---------------- | ----------------- | ------------------------------ |
| Customer         | Phone + text code | No password needed             |
| Seller           | Phone + text code | Email also verified at sign-up |
| Delivery partner | Phone + text code | Documents verified at sign-up  |
| Admin            | Email + password  | Traditional login              |

---

## Phone + Text Code Login

Used by customers, sellers, and riders.

### How it works

1. User enters their phone number
2. System sends a short code via text message
3. User enters the code
4. If correct, user is logged in

### Security features

- Codes expire after a few minutes
- Codes are single-use — cannot be reused
- Too many wrong attempts temporarily blocks login
- Each phone number has only one account

### Why no passwords?

- Easier for users — no password to forget
- Phone number is already a unique identifier
- Text code proves the person has access to the phone

---

## Admin Email + Password Login

Admins use traditional email and password login because:

- Admin accounts need stronger security
- Admins access sensitive business data and financial tools
- Password can be changed regularly for security

### First admin setup

The very first admin account is created using a special setup key — only someone with this key can create the initial admin. After that, existing admins can create new admin accounts.

---

## Role Separation

The system enforces strict role boundaries:

| Rule                                  | Example             |
| ------------------------------------- | ------------------- |
| Customer cannot access admin panel    | Shopping app only   |
| Seller cannot see other sellers' data | Only their own shop |
| Rider cannot manage products          | Delivery app only   |
| Admin can see everything              | Full access         |

Every action checks who is logged in and whether they are allowed to perform that action.

---

## Approval Gates

Some roles require admin approval before full access:

### Sellers

- Can sign up and submit application
- Cannot list products or receive orders until approved
- Prevents fake or unauthorized shops

### Delivery partners

- Can sign up and upload documents
- Cannot go online or accept jobs until approved
- Prevents unverified riders from delivering

---

## Delivery Code Security

### Why delivery codes exist

Without a code, a rider could mark an order as delivered without actually reaching the customer. The delivery code prevents this.

### How it works

- Code is generated by the system (not chosen by customer or rider)
- Code is shown only to the customer on their order page
- Rider must enter the correct code to confirm delivery
- Wrong code = delivery not confirmed

---

## Payment Security

### Online payments

- Customer is redirected to the payment partner's secure page (not handled on the platform directly)
- Payment partner confirms transaction directly to the platform server
- Platform verifies payment before advancing the order
- Fake payment claims are rejected

### Cash on delivery

- Rider must confirm exact amount collected
- Cash is tracked as "cash in hand" — cannot disappear
- Admin reconciles cash against orders

### Double-charge prevention

- Each checkout has a unique identifier
- Duplicate payment attempts are ignored
- System matches payment confirmations to specific orders

---

## Rate Limiting

The system blocks abuse by limiting how many requests one person can make:

| Action              | Limit                            |
| ------------------- | -------------------------------- |
| Login code requests | Few per minute per phone number  |
| Wrong code attempts | Blocked after several failures   |
| Order placement     | Reasonable limit per customer    |
| API requests per IP | General limit to prevent attacks |

---

## Data Privacy

- Customers can only see their own orders and data
- Sellers can only see their own products and orders
- Riders can only see their assigned deliveries
- Admin access is logged
- Location data is cleaned up after deliveries
- Support tickets are private between customer and admin

---

## What Happens Behind the Scenes

- Login creates a secure session token (like a temporary pass) that expires after a set time
- Every request checks the token and role before allowing action
- Text codes are hashed — not stored as plain text
- Payment confirmations are verified with the payment partner directly
- Failed login attempts are counted and blocked

---

## Important Rules

- Never share admin login credentials
- Text codes are single-use and time-limited
- Delivery codes prevent fake deliveries
- Payment verification happens server-side only
- Approval gates must not be bypassed
- Rate limits protect against abuse

---

## What If Something Goes Wrong?

| Problem                  | What to do                                        |
| ------------------------ | ------------------------------------------------- |
| User locked out of login | Wait for rate limit to expire; contact support    |
| Admin forgot password    | Use password reset or another admin resets it     |
| Suspicious seller/rider  | Do not approve; investigate documents             |
| Fake delivery reported   | Check delivery code records; contact rider        |
| Payment dispute          | Check payment partner records; compare with order |
